# Monthly Infinity breach warning — 8 October 2026

After an Infinity failure, every attempted Infinity market/pending order reopens **Account has been breached** with the next eligible date. Closing that notice never removes the block. Requested challenge intent is kept separately from the automatic practice-account fallback, so a failed order cannot silently be reported as a Demo fill. Explicitly choosing Demo permits practice; returning to Challenge shows the warning again. Old success messages for backend-blocked acknowledgements are suppressed.

`fn_infinity_breach_lockout(user)` derives the deadline from the newest actual Infinity breach timestamp/event, ending at the first of the next **UTC calendar month**. A failure on 8 October blocks until 1 November 2026 00:00 UTC, even if the original run started in September. A December failure resets in January. The person mapping includes suspended duplicate aliases. An unknown failure time requires review rather than a guessed deadline. The old failed account never reactivates; a new challenge still requires existing approval/identity/attempt eligibility.

Migration `20261008140017_infinity_monthly_breach_lockout.sql` protects challenge-account insertion, new Infinity trades/pending orders and continuation checkout source links when the source column exists. The hosted checkout schema currently lacks that column; this repair does not add or activate paid continuation infrastructure. The engine supplies lockout data in state/eligibility replies and rejects challenge entry before trading; triggered pending orders pause while expiry/close/risk reduction remain available. Restart/continuation controls are disabled during the block. Existing paid-order status updates are preserved, while new challenge provisioning remains blocked. No payments/refunds, Terms, passwords, broker orders or model selections are performed by this rollout.

Tests cover repeated dismissal/attempts, no false filled acknowledgements, explicit practice, exact month boundary, year rollover, aliases, API/SQL bypass rejection, source-link rejection and unknown timestamps. Private drift checks/rehearsals preserve the deployed engine and shared dependencies. The generic breach dialog cannot cover the recurring warning, and passive polling does not permanently dismiss the attempt warning.
